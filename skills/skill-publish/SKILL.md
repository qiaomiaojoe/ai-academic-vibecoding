# Skill 库发布

输入：要发布哪些 skill、仓库地址（没有就先建）、可见性、执行平台。独立可用，不要求工作台或设计文件。

面向的起点是**刚注册好 GitHub 账号**：可能没装 git、没配过认证、没建过仓库。按这个前提说话，不默认用户懂 git。

## 1．发布前体检（不体检不发）

推之前逐个读要发布的 SKILL.md 及其支持文件，列出下列命中位置交用户决定删改：

- 未发表稿件片段、审稿意见原文、期刊内部往来
- 学生、被试、合作者可识别信息；真实姓名与单位
- 本机绝对路径（含用户名）、token、API key、内部地址

**用户没看过体检结果就不发。** 命中不自动删改——删哪条是作者的判断。

**public 一旦推上去就是公开的**，之后删掉也可能已被抓取或收录。可见性选 public 前必须说破这一条。

## 2．建库与认证：用户自己做

- **仓库由用户在网页自己建。** 不代建账号、不代填密码、不接触 token 或恢复码。
- **可见性由用户定。** 默认建议 private——方法是作者的私产；用户要 public 就按 public，但先讲清第 1 节那句。
- **认证由用户自己完成**（如 `gh auth login`，或系统凭据管理器）。AI 只跑 git 命令；认证失败如实报告并说明该怎么做，**不绕过、不把凭据写进文件或命令行、不改全局凭据配置**。

## 3．库的结构

```
skills/<name>/SKILL.md      # 一个 skill 一个目录，支持文件放同目录 references/
README.md                   # 这是什么、怎么装、每个 skill 一行说明
```

- `name` 用小写连字符，**与目录名一致**。
- **不用符号链接。** Windows 上 `ln -s` 要么没有，要么静默拷成两份。
- **库里只放方法。** 业务项目、产出、日志、材料原文一律不推。

## 4．推送

先看远端是不是空的。非空先说明本地与远端的差异再合并；**不强推、不覆盖远端已有内容**，远端有本地没有的东西时停下问。提交信息写清这次推了哪些 skill。

## 5．验证闭环：装回来才算数

换一个空目录从远端取回，逐个核对：文件齐、正文与本地一致、frontmatter `name` 与目录名一致。

**装不回来的库等于没有。** 私有库还要确认换一台没有当前认证的机器该怎么取——说不清就是没验完。

## 6．增量与记录

新造的 skill 增量推；改过的先看远端有没有别处的改动，有就先说明差异。删 skill 要用户明确点名，不顺手清理。

记仓库地址、可见性、最后推送日期、已发布 skill 清单，写进项目设计或 `AGENTS.md` 备查。

推送成功、页面能打开，都不等于库可用——以第 5 节装回来的结果为准。
