# Skill 库发布

输入：要发布哪些 skill、仓库名或地址（没有就由你建）、可见性。独立可用，不要求工作台或设计文件。

**总原则：GitHub 上的一切由你做。** 建仓库、初始化、提交、推送、拉取、核对，全部你用 `gh` / `git` 完成，不要让用户去网页上点。用户只做两件事：**一次登录授权**，和**拍板发布什么内容**。

面向的起点是刚注册好 GitHub 账号：可能没装 `git`、没装 `gh`、没配过认证。按这个前提说话。

## 1．发布前体检（不体检不推）

推之前逐个读要发布的 SKILL.md 及支持文件，列出下列命中位置交用户决定删改：

- 未发表稿件片段、审稿意见原文、期刊内部往来
- 学生、被试、合作者可识别信息；真实姓名与单位
- 本机绝对路径（含用户名）、token、API key、内部地址

**用户没看过体检结果就不推。** 命中不自动删改——删哪条是作者的判断。

## 2．打通通道（你来做）

按顺序自查并处理，每步把实际结果告诉用户：

1. **`git` 和 `gh` 在不在。** 缺了就按用户平台给出安装命令并执行（macOS `brew install gh`；Windows `winget install GitHub.cli`；Linux 按发行版）。
2. **`gh auth status` 是否已登录。** 没登录就**由你发起** `gh auth login`，让用户在 GitHub 自己的页面上完成授权。
   **这一步是唯一需要用户本人动手的地方**——因为要输入他自己的凭据。
   **你不要索取、代填、转述或存储 token 和密码，不要把凭据写进文件或命令行。** 授权完成后回到自动流程。
3. **仓库在不在。** 没有就你来建：`gh repo create <名字> --private`（名字没给就建议一个，如 `my-academic-skills`）。
   已有同名仓库先说明，不覆盖、不改名。

**可见性默认 private。** 用户要 public 才用 public，并先说破：**推上去就是公开的，之后删掉也可能已被抓取或收录。** 不要擅自把已有仓库从 private 改成 public。

## 3．库的结构

```
skills/<name>/SKILL.md      # 一个 skill 一个目录，支持文件放同目录 references/
README.md                   # 这是什么、怎么装、每个 skill 一行说明
```

- `name` 用小写连字符，**与目录名一致**。
- **不用符号链接。** Windows 上 `ln -s` 要么没有，要么静默拷成两份。
- **库里只放方法。** 业务项目、产出、日志、材料原文一律不推。

## 4．推送与更新（你来做）

初始化、add、commit、push、pull 都由你执行，提交信息写清这次推了哪些 skill。

先看远端状态。非空就先说明本地与远端的差异再合并；**不强推、不覆盖远端已有内容、不删仓库、不碰用户的其他仓库**。远端有本地没有的东西时停下问。

## 5．验证闭环：装回来才算数

换一个空目录，由你从远端取回，逐个核对：文件齐、正文与本地一致、frontmatter `name` 与目录名一致。

**装不回来的库等于没有。** 私有库还要确认换一台没有当前认证的机器该怎么取——说不清就是没验完。

## 6．增量与记录

新造或磨过的 skill 增量推；改过的先看远端有没有别处的改动，有就先说明差异。删 skill 要用户明确点名，不顺手清理。

记仓库地址、可见性、最后推送日期、已发布 skill 清单，写进项目设计或 `AGENTS.md` 备查。

推送成功、页面能打开，都不等于库可用——以第 5 节装回来的结果为准。

## 没有 gh 时的退路

`gh` 装不上（受限环境、公司机器）时才退回：让用户在网页上建一个空仓库、给你地址，其余推送与验证仍由你完成。**这是退路，不是默认路径**，走了要说明为什么。
