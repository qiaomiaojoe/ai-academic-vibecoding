# Skill 工坊：制作、修订与整合

输入目标职责、材料路径或口述、新建/修订、目标平台。接回工作台还需项目、设计与场景；没填场景可从设计定位，多个候选才问。独立制作不要求工作台或设计文件。

## 0．第③讲：按待造清单批量固化

**输入源是 `工作台设计.md`**——它带全部待造 skill 名、所属场景和完整方法正文。工作台入口页的「要造的 skill」清单给名字与场景，正文以设计文件为准；设计文件缺正文时回退读场景卡内联正文，并提醒补进设计。

两种节奏由用户选，不替他决定；没说时按**批量**做，一次跑完就是本讲的目的。

### 批量（一次跑完全部）

1. **先一次性评估，再一次性批。** 读完全部待造项，出一张评估表：每个 skill 该不该独立存在、职责边界对不对、要不要与相邻场景合并或拆分、名字是否还贴切。**用户在这张表上一次批完，不要每个 skill 停一次。** 改名与合并按批复执行，同步更新场景卡与设计。
2. **批量生成。** 按第 2、3 节逐个补齐触发条件、分支、完成标准、硬约束、作者决定点、异常处理和典型失败模式，并满足第 3 节那三条硬规格。**先在设计文件里找一个已经写到这个规格的角色当范本**（判定分类、输出成表、点名失败模式都齐的那个），拿它对齐其余角色，别让任何一个停在一段职责描述。内联正文是初稿不是成品；已确认的做法要保留，不得借“规范化”之名改写成通用模板。
3. **批量造可以，批量验收不行。** 生成完接回场景：状态从待造改**已建**，该场景指令改为引用 skill 名、不再内联正文。**已建不等于已验**——至少挑一个实际生成一次该场景的 prompt，核对确实读到新方法；其余一律标**未验证**，逐个验过才能记已验。一次生成一堆没验过的空壳，等于没造。
4. **逐条交代。** 造了哪些、改名或合并了哪些、验的是哪个、还剩什么没验，一次说清。

### 逐个（一次一个）

用户点名某个 skill，或评估发现职责冲突需要边造边定时，按上面四步只跑那一个。

清单为空或工作台没有该清单时，按下面各节的常规模式处理。造好的 skill 要进用户自己的 skill 库时交 `skill-publish`，本 skill 不做发布。

## 1．定位与核对

项目模式先确认根目录，读项目指令、`工作台设计.md` 或指定设计、目标场景输入输出及停点。根目录未给时只按项目名在当前目录及直接子目录定位，缺失或多匹配问清。相对路径以项目根目录为准。

修订先读旧 skill 及引用文件，列当前问题、新材料、需要保留的行为。检查全局同名执行副本及其他场景引用，不把修订变成抹掉用户改动后从头生成。

材料可混合，按真实内容识别来源与用途。读取失败报告准确路径与原因；经验访谈不强制要 PDF 或文件夹。缺职责时先给候选草案。

## 2．按材料加工

| 材料 | 提炼方式 | 特别检查 |
|---|---|---|
| 经验/口述 | 整理步骤、判断和例外；每轮最多三个关键问题，附草案 | 区分本人做法、AI 建议、待确认，不伪称来源 |
| 期刊指南/投稿规范/机构要求 | 提取适用对象、必须项、建议项、例外、格式、提交前检查 | 记机构/期刊、版本或日期、来源路径/URL、查阅日期；不同刊要求不混成通则。需要最新要求就查官方来源，无法联网则标未核实最新 |
| 成功案例/修改前后稿 | 对照输入、处理决定和结果，提炼做法与适用条件 | 个案不自动推广，事后选择不伪装成规范要求 |
| 教科书/方法论文 | 按任务读相关章节，提取触发条件、输入、步骤、输出、易错点和原文位置 | 有页码实测页码；无页码用标题/段落/条款。统计门槛仅在原文涉及且与任务相关时提取 |
| 已有 skill | 根据新材料、失败案例与设计定向修改 | 保留有效规则与支持文件，查冲突、重复、过期要求和下游接口影响 |

不凑固定数量的筛选准则、疑点或步骤。短规范直接提炼；长材料按相关部分分批读并保存提取记录，不把所有中间稿只留在模型上下文。

## 3．形成可执行方法

先提出职责、适用范围与关键冲突；已有明确要求直接遵循，真正涉及学术判断的歧义才等用户决定。建议与确定规则分开。

方法包含：何时用、输入要求、必要步骤与分支、可观察完成标准、硬约束、软偏好、作者决定点、异常处理、输出结构、**典型失败模式**。保留 may/consider/通常/建议等软词；不得遗漏表注脚注的有效要求。不凭“最高优先级”几个字假设规则一定执行。

**三条硬规格，不满足的是半成品：**

1. **判定分类，每类带默认动作。** 不写「检查 X 是否一致」，写「一致 → A；有出入 → B；查不到 → C」。
2. **输出写成字段名或表头**，不写「输出结果」。两次跑形状一致，下游才接得住。
3. **典型失败模式点名到具体那一处。** 硬约束说「不许做 X」，失败模式说「你会想做 X，因为 Y」——后者对执行的 AI 有效得多，也是把作者踩过的坑真正留下来的地方。

自查：正文出现「注意」「记得」「记在日志里」的，基本都是还没做成机制的洞，改成必须产出的字段或必经的步骤。

短方法写 SKILL.md，长来源说明与分支放 references/ 并按需引用。frontmatter name 用小写连字符、与目录一致；description 写真实用途。不要强制每步一文件。有可用 skill-creator 可使用，没有也能按本节产出自包含 skill，不硬依赖未安装插件或固定脚本路径。

修订给出关键差异、保留项、接口变化与影响场景。核心方法未定则标待补，不编造结论。展示完整 SKILL.md，长支持材料给目录与关键差异；用户确认方法后定稿。已确认规则和已授权明确修复不重复审批。可保存清楚标为草稿的文件，不冒充确认执行版。

## 4．保存与接回场景

- **项目模式**：源默认 `skills/<name>/SKILL.md`，提取记录在 `skill源材料/`。开发中场景可明确读取项目源文件执行。需平台发现时，Claude Code 用 `~/.claude/skills/`，Codex 用 `${CODEX_HOME:-$HOME/.codex}/skills/`；记源路径、执行路径、版本/校验值。比较同名内容，不同则保留唯一备份，获得更新授权后同步，不能覆盖其他项目定制方法。
- **独立模式**：指定路径优先，否则按目标平台使用全局目录。同名不同内容先说明差异、影响，再决定修订或新名。
- **整合**：只改设计明确对应的场景，更新 skill 引用、实际读取路径及输入输出。写上名称不算绑定完成。接口变更同步相关上下游与设计；只授权制作不擅改其他工作台。
- HTML 变动时备份、提高版本并记 CHANGELOG；纯方法修改记方法版本及绑定，不虚增 HTML 版本。

## 角色执行绑定

若项目含 `工作台配置.json`，从设计定位实际 role ID 与所属步骤。将确认方法的必要正文写入对应 `roles[].instructions`，登记源 skill 路径、版本或校验值到设计；当前正文适配器仅填写 skill 名/路径不会读取方法。长方法按职责拆分或扩展专用读取适配器，不能截掉有效条件。

核对角色 summary/content/decision 接口；同组角色相互独立，需读取另一角色结果时安排下游步骤。把客观条件和人工判断写入对应 checks，AI 的 pass 建议不代替证据。源方法修改同步受影响角色配置、配置版本及设计，再用新任务复测；旧任务的配置快照不暗改。

## 5．验证与交接

检查 frontmatter、名称、引用文件和模板残留；有校验器就运行。用职责对应的正常材料及一个关键边界试跑，例如指南缺项、原稿不存在、尚未补分析。按设计停止或请求决定，不编造缺失信息。

记录输入、实际执行版本、输出和观察结果。模拟示例或格式检查不能写成实际通过。项目模式从工作台生成的 prompt 调用一次，核对确实读到新方法，更新设计里的绑定与验证状态。整体业务联调交 workbench-validator；缺依赖给明确交接，不宣称已整体验收。
