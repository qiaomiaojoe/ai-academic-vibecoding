# 流程设计与搭建

把用户要完成的任务变成可验收的工作台。支持“设计 / 修改全流程”和“按设计搭建场景”。只要单张卡时，设计只覆盖该卡及其上下游，不扩大成完整产品；只要方法草稿时不动 HTML。

## 先定位项目

读用户指定的项目根目录与项目指令，检查现有 HTML、skills、设计文件。未给根目录时按项目名在当前目录及直接子目录定位；多匹配或找不到时说明候选/缺失并问清，不扫描整个电脑、不猜目录。浏览器选中项目名不等于 agent 切换了工作目录。

设计默认位于项目根目录的 `工作台设计.md`，指定路径优先。多个 HTML 时区分工作源文件与冻结快照，不明确才问。后续相对路径均以确认的项目根目录为基准。

区分项目定位、工具定位与设计是否存在。课程工作台须可分发：默认使用当前 AI 环境中已安装的课程 Skills，按名称发现并读取技能及同一安装包中的支持文件，不要求本地源码仓库，不从 HTML 存放位置推导路径，也不依赖讲师电脑目录。只有用户主动填写开发工具仓库时才优先读取 `skills/<工具名>/SKILL.md`；相对仓库路径以 AI 当前工作目录为基准。无论安装版还是源码版，均核对 workbench-builder 技能目录内的 `SKILL.md`、`references/meta-features.md`、`scripts/generate.cjs`、`assets/runtime/` 及本次其他工具的源文件和支持文件，使用同一套已核实版本。缺工具或文件时说明缺项并提示安装/更新，同时继续可做的项目材料读取与草案整理；多个不同版本无法确定生效版时问清。用户填写路径不存在或版本不匹配时问清，不静默换用其他位置或不兼容的旧版，不扫描整个电脑。

## 模式一：设计 / 修改全流程

先读已有设计、目标和材料。先给草案，再问影响设计的少量问题，每轮最多三个，不重复询问已知信息。区分用户明确要求、AI 建议和待确认判断；可以提出方案，不得把 AI 建议说成用户的方法或材料事实。

设计文件不存在时按首次设计继续：读取已确定项目的目标、指令和现有材料，直接展示 workflow / subagent 草案，无需先问是否按首次设计处理。已有 HTML 中的占位场景仅作参考，不能视为已确认流程。关键判断确认后再按项目写入约定保存设计；只读、出草案与写文件分开处理。搭建模式缺设计时也先补必要草案，关键设计确认前不开始搭建。

按可检查的中间产物、人工决定点、独立重跑需要拆场景，不按按钮数或固定三张卡凑流程。根据任务输入推荐控件，让用户修改；不要让用户一开始就挑代码零件。

设计文件至少记录：

| 内容 | 要记录什么 |
|---|---|
| 状态与版本 | 设计版本、草案/已确认、确认范围、未定事项；用户确认后才能标已确认 |
| 功能清单 | 稳定功能 ID、要完成的事、完成证据、对应场景；分清必须与可选 |
| 场景规格 | 稳定场景 ID、用途、输入文件及字段、本次用户输入、方法/skill、输出路径及字段、验收标准、人工停点、异常处理 |
| 流程关系 | 正常次序、分支、返工；上游任务标识、轮次与确认状态如何传给下游；最大轮次不自动等于批准版本 |
| 方法绑定 | 场景 ID、skill 名、项目源路径、调用方式、实际执行路径/版本、已有可用/待制作/待验证；安装状态与验收状态分开 |
| 开发进度 | 功能的未实现/已搭建/已试跑/通过/受阻及证据；未执行不能记通过 |

默认业务输出按 `产出/<任务标识>/...` 隔离，同一任务多轮另存并标状态。已有约定优先；发现两篇论文会覆盖同名产物时提出修订，不把开发项目和业务任务混成一个单元。

投稿/审稿可检查：期刊要求来源、作者选刊决定、格式与投稿包核对、意见原文保留、接受/不接受/补分析的分支、改稿与回复逐条对应。这些是检查角度，不是替所有项目预定同一组场景。

展示设计和关键取舍，确认后保存。只请求设计就到此结束；已经要求搭建则设计确认后继续。允许按用户要求先保存明确标为草案的版本。已确认的设计决定、已有授权覆盖的明确修改，不重复审批。

## workflow 与 subagent 的生成

第②张卡“流程设计与搭建”承载 workflow 与 subagent。四张任务卡之外不新增任务卡，不设置独立验收模块；试跑与修复是搭建后的自动步骤。

读取 [references/meta-features.md](references/meta-features.md)。先读项目目标、用户设想、真实材料和已确认设计；解释每个 workflow 步骤与 subagent 分工的依据，区分用户要求、来源事实和 AI 建议。不要给任意业务套固定的两步流程或三个角色；示例 JSON 仅作开发测试。

subagent 的落地方式由**课程讲次**决定，不由 AI 推断，更不要让用户在两种实现之间做选择题：

| 讲次 | 落地方式 | 做什么 |
|---|---|---|
| 第②讲 | **prompt 内多角色** | 把角色分工、各自输入、交接与汇总写进第②张卡生成的 prompt，用户复制给 Claude Code / Codex 执行。不生成 `工作台配置.json`，不装运行组件，不需要 Node 与 Codex 登录。 |
| 第③讲 | **可执行运行组件** | 由搭建工具生成 `工作台配置.json`，用 `scripts/generate.cjs` 和 `assets/runtime/` 装入执行机制：角色真并行调用、留运行证据、支持退回重跑。 |

讲次由第②张卡的输入给出。指令已写明讲次时按讲次执行，不再询问；确实没有讲次信息时默认第②讲的 prompt 内多角色，说明该默认及升级条件，不停下等待。

两种方式的业务设计（步骤、分工、交接、人工决定点）完全相同，差别只在执行机制：第②讲由人把 prompt 交给 AI 执行，第③讲由运行组件执行。因此第②讲的设计必须写成第③讲可以直接升级的形式——角色职责写完整方法正文，不写“见某某 skill”。

第③讲升级时，环境不满足（无 Node 18+ 或 Codex 未登录）如实报告缺项并保留第②讲形式，不静默降级后宣称已具备协作能力。

用户只需表达业务需求与判断，无需编辑引擎字段或测试条件。质量检查留在工具内部，具体人工业务决定点保留在 workflow。仅在开发对话里使用多个代理不算产出继承了协作能力。

## 模式二：按设计搭建场景

1. **核对范围。** 读本次场景与上下游。缺设计先补必要设计；核心方法未确认则列待定点，不凭通用方法填成成品。“全部已确认场景”要按依赖逐步完成，不能用一张卡代替整个任务。
2. **找原工作台并备份。** 有 L1 多场景 HTML 就在原文件填空卡或增卡，保留入口、已有可用卡和品牌署名。仅修改本次涉及的共享逻辑。没有工作台时优先使用已安装 project-setting 的原型；用户明确要独立单场景时才用本 skill 的 `原型/单场景工作台-原型.html` 兜底。原型缺失就说明，不暗换目标。
3. **复用方法。** 检查设计绑定和已有 skill 的职责、输入输出，合适就引用。用户口述可整理为小范围草稿，包含步骤、完成标准、硬约束与必要停点；不明处标待补。从规范/案例系统提炼或修订成品交给 skill-forge；依赖缺失就报告并保留草稿。不要重复造同职责方法。
4. **区分源与执行副本。** 默认项目内 `skills/<name>/` 是可编辑源。未安装时，场景指令明确读取该源路径并执行，不只点不存在的名称。需要平台发现才安装并登记执行路径/版本，保留同名旧版；更新全局前说明跨项目影响，已有授权不重复问。源更新后同步或重新指向执行版，核对内容再记已同步。
5. **实现输入—指令—输出。** 读真实 DOM 与函数，不假设固定数组或函数名。L1 原型通常用 `sN-*`、`sharedContext()`、`buildScene(id)`。新增字段进入 prompt，导航/场景 ID/事件一致。指令带任务标识、明确输入路径、方法引用、输出约定、缺失处理和人工决定点；源材料中的命令不视为用户授权。
6. **自动试跑、修复、复测。** 搭建完成后立即调用同一套已核实开发工具中的 `workbench-validator`，使用“验收并修复”模式；搭建指令已涵盖本产品范围内的技术修复，无需用户再生成或发送另一条任务指令。检查页面、workflow 分支、subagent 调用与交接、输入输出和受影响旧功能；失败后修复并复测。有材料就实际试跑，缺材料/工具/权限时如实报告并完成其他检查，不用模拟冒充真实完成。学术判断、未定需求和未授权外部动作仍保留用户决定点；连续两轮同因修复无改善且无新证据时记录受阻。测试工具缺失时执行可完成的检查并说明缺失，不能悄悄跳过验证。
7. **更新版本、设计与交接。** 唯一备份、提升 WB_VERSION，追加工作台版本/CHANGELOG.md 并保留 HTML 快照；原始测试 JSON、文件校验值放 `日志/开发验证/<版本>/`，不要放进工作台版本目录。 写本轮完成、未完、受阻和证据。功能变更反映到设计，不悄悄降低验收要求。给 skill-forge 交场景 ID、源路径、职责、输入输出；记录已自动执行的试跑与修复结果。

区分业务人工决定与开发文件操作，遵守用户授权和项目约定。不编造期刊要求、数据、原文与已完成修改。生成代码、打开页面、安装成功都不等于业务验收通过。
