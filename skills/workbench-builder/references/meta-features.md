# workflow 与 subagent：设计、生成、自动试跑

用于第②张卡“流程设计与搭建”。workflow 安排业务步骤和交接，subagent 承担实际分工；搭建后由工具自动试跑、修复和复测，不再提供独立验收模块。

## 设计的来源

依据用户目标、填写的设想、项目材料与既有设计生成。每项设计注明依据与 AI 建议。v1.2 的两步流程和三个角色来自开发者手写的 `../assets/workflow.example.json`，仅供机制回归测试；不能把它预填成任何业务的方案。

网页中的 workflow / subagent 是可选草案区，默认留空；页面不自行读取磁盘或调用模型，用户将第②张卡指令交给 Codex 后，由 skill 读取项目并设计。保留已有自定义草案，不能因升级清空用户改动。

## 由搭建工具维护运行配置

`工作台配置.json` 继续使用 schemaVersion 1。以下是内部运行协议，不要求学员填写。界面名为 workflow / subagent，底层 steps / roles 键保持兼容。checks 由搭建工具按实际设计维护，作为运行检查与必要业务决定点，不作为第三个开发模块。

| 字段 | 约定 |
|---|---|
| name / version / start | 产品名称、配置版本、起始步骤编号 |
| roles[] | id、name、instructions（真正进入角色上下文的方法正文，不能仅写 skill 名或路径） |
| steps[] | id、name、roles（同一步 1–4 个独立角色）、next（通过去向/null 结束）、failTo（退回去向/null 停下）、maxAttempts（1–5）、checks |
| checks[] | 全局唯一 id、name、type；nonempty / contains 绑定本步 role，contains 还需 value；human 记录人的判断 |

编号使用小写字母开头及数字/连字符，不使用 constructor / prototype。通过路径必须可结束，所有步骤应可到达；返工循环受执行次数限制。生成器用 `assets/runtime/engine.js` 校验运行配置。

先确认输入、输出、方法、角色交接和业务判断。已授权明确设计无需重问。流程与方法有未定项时可保存草案，但不能把占位符生成成已验收的方法。

同一步的角色看相同输入和已验收上游，不能看到同组尚未完成的结果。复核某角色产出或汇总分歧必须另设下一步。每个角色返回 summary、content、decision（pass/fail/review）；decision 只作建议，不能替代验收。任何 fail/review 都停在人工判断；非空/关键词仅证明对应形式条件，学术正确性用明确人工验收。独立角色不等于独立事实来源。

## 生成与整合

从本 skill 目录执行（实际调用用核实的绝对路径，参数分别引用）：

```sh
node scripts/generate.cjs /项目/工作台配置.json /项目/工作台/运行组件-v1
```

生成器拒绝已有目录，不覆盖自定义组件、运行证据或旧版。产出包含 workflow.json、engine.js、adapter.cjs、server.cjs、index.html、app.js、style.css、manifest.json、使用说明.md。manifest 保存组件版本、配置版本及文件校验值。

**新产品**可从生成的面板继续搭建。**已有产品**先生成到临时/版本目录，把运行面板及事件逻辑整合回原工作源 HTML，保留原入口、场景及品牌；让本地服务的 index.html 对应整合后的原页面。不要交付第二个空泛演示页替代原产品。修改静态资源映射时检查旧页面依赖是否可被本机服务访问，不开放任意目录读取。整合改动同步 manifest 中受影响文件校验值。

运行方式：Node.js 18+；`node server.cjs --demo` 验证机制；`node server.cjs` 使用本机已登录 Codex。打开终端给出的完整本机链接，点击执行才调用模型。可用 CODEX_BIN 指定可执行文件，WORKBENCH_MODEL 指定可用模型，不强行更改全局模型配置。未指定模型时使用 CLI 默认模型。服务只监听 127.0.0.1，使用会话令牌与同源检查。

当前 Codex 适配器通过 `codex exec` 的标准输入与结构化输出工作；只用正文、已验收上游和返工意见，禁用用户配置注入的插件并使用 read-only sandbox。角色职责需包含所需方法内容。不会自动解析文件路径，不提供任意命令、连接器或外部发送工具。若项目需要解析 PDF/Word 或调用外部工具，按明确需求增加专用适配器，约定输入输出与授权边界并真实验证，缺失时标受阻。

依据：[Codex 非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)（2026-09-09 核对）；实际机器还需核对 `codex exec --help` 是否支持 --ignore-user-config、--ephemeral、--output-schema。登录与账号可用性不由生成器保证；运行失败记录错误，不能静默切换到 demo。

## 运行证据与版本

- 每次任务保存配置快照、模式、组件版本、输入、角色结果、程序检查、人工决定和时间；在 runs/demo 与 runs/codex 隔离。已验收上游才传给下游；退回目标及其后续结果失效，旧证据仍在历史中。
- 保存步骤状态与角色进度。服务重启时，中断的步骤标失败，由用户重试；完成步骤不自动重新调用。重复点击和旧 revision 请求拒绝执行。
- 改配置只影响新任务，旧任务按自己的配置快照继续。更新引擎需考虑旧记录格式；先备份并迁移或保留旧引擎目录，不默认兼容未来版本。
- 交付前分别验证生成器、运行机制、真实角色和业务目标。模拟模式不能证明方法有效，生成页面不能证明已具备全部业务能力。

## 搭建后自动试跑与修复

检查无效引用/通过环/不可达步骤；正常通过及失败退回；同组并行与下游汇总确实收到已验收输出；角色错误/超时/格式错误不放行；分歧与人工验收必须记决定；程序失败不能被人工通过按钮绕开；次数上限、重复提交、任务隔离、重启恢复、配置版本快照；文件清单与校验值。对照业务设计补真实样例，不以通用示例取代业务验收。

搭建工作包含本产品技术问题的修复与复测。不要等用户另发测试指令，也不新增测试任务卡。设计模式只产草案，不运行搭建或试跑。遇到业务决定或外部动作仍按授权处理；环境受阻如实报告。文件校验值、模拟记录等开发证据归入 `日志/开发验证/<版本>/`；版本目录保留快照及 CHANGELOG。
